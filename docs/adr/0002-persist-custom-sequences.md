# Persist custom chord sequences in an embedded SQLite database

The chord-sequence page currently gets its catalog from two hardcoded places: the six concatenated keys in `main.py:40-45` and four of those sequences repeated in `static/assets/js/controllers/sequencia.js:2-37`. Search does not compute a match at request time at all; it resolves one of those keys and filters the precomputed `seqs_famosas` tag loaded from the CSV (`main.py:190-223`). Because there is no database and the Dockerfile declares no volume (`AGENTS.md:9-11`, `Dockerfile:1-12`), anything registered at runtime would disappear when the container restarted. The feature request requires an open, anonymous catalog that survives restarts while songs and genres keep coming from the CSV-loaded in-memory structures (`docs/features/sequencias-customizadas/00-enunciado.md:47-67`).

We decided to introduce persistence only for the sequence catalog, using the standard-library `sqlite3` module in a single file under `/app/var` (`SEQUENCES_DB_PATH`, default `var/sequences.sqlite3`). SQLite was chosen over `shelve`/`dbm` because it adds no dependency to `requirements.txt:4-5`, still fits the single local-only container from ADR 0001, and gives us a unique key for normalized chord sequences plus an ordered, inspectable catalog. The six existing sequences are seeded idempotently with their current IDs and legacy keys, so `BmGDA` and `Bm,G,D,A` keep resolving to the same songs; new sequences are stored as ordered chord lists and matched at request time against `musica.cifra` using the generator rule in `scripts/generate_data_set.py:7-24` — the only definition that reproduced all 514 tagged songs with zero false positives and zero false negatives in `research/01-research-findings.md:24-34`.

The database is deliberately not a home for songs or genres: `main.py:49-98` continues to read `data/top/dataset_final.csv` once at import, and `/generos` still exposes that in-memory data (`main.py:158-160`). To make the catalog survive a container restart and a recreation with the documented command, `Dockerfile` declares `VOLUME /app/var` and the run instructions use a named volume such as `ciframe-sequences:/app/var`; `.dockerignore` excludes the local `var/` directory so a developer's test database is not copied into the image by `COPY . .` (`Dockerfile:8`). No cloud service, second container, or migration framework is introduced, preserving the deploy decision recorded in `docs/adr/0001-local-only-docker-deploy.md:9-16`.

The trade-off is that state now has a lifecycle of its own: volume ownership and backup become operational concerns, anonymous users can grow the catalog without moderation, and the app must validate and deduplicate input before writing. Search stays a scan over the in-memory song catalog, which is acceptable for the current single-worker gunicorn process (`Dockerfile:12`) and the 67,585 songs loaded from the CSV, but a future multi-worker deployment would revisit locking and WAL settings. We also keep every response as a `json.dumps(...)` string, so the API preserves its existing `text/html` behavior instead of silently changing content type.
